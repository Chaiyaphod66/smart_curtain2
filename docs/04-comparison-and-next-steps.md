# เปรียบเทียบ Auto และแผนพัฒนาต่อ

## ตารางเปรียบเทียบ

| เรื่อง | Auto Preset ปัจจุบัน | Model A |
|---|---|---|
| สถานะ | ใช้จริงบน ESP32 | ใช้จริงบน ESP32 |
| ทำงานเมื่อปิดเว็บ | ได้ | ได้ |
| วิธีใช้แสงและอุณหภูมิ | อุณหภูมิมีสิทธิ์ปิดเหนือแสง | อุณหภูมิกำหนดงบแสง |
| เป้าหมาย | Absolute เช่น 15/40/65/90% | Step จากตำแหน่งปัจจุบัน |
| ร้อนแต่มืด | ปิดตามเกณฑ์ร้อน | คงตำแหน่ง |
| ป้องกันค่าแกว่ง | Confirmation + Cooldown | Temperature hysteresis + adaptive step |
| ความง่ายในการตั้งค่า | ง่ายและมีชุดสำเร็จรูป | ต้องอธิบาย Profile มากกว่า |
| ความนุ่มนวล | อาจเคลื่อนไกลหนึ่งครั้ง | เคลื่อนหลายรอบทีละขั้น |
| ความปลอดภัยจริง | เชื่อมกับ firmware และฮาร์ดแวร์แล้ว | ใช้ safety layer ชุดเดียวกันบน ESP32 |

## ข้อสรุปปัจจุบัน

- Auto Preset และ Model A เป็นทางเลือกที่ผู้ใช้เลือกได้ โดยทั้งสองแบบทำงานบน ESP32
- Model A ใช้ Confirmation 2 รอบ ขยับทีละ Step และ Cooldown 15 วินาที
- หน้า Dev ใช้ตรวจเหตุผลและสถานะ ไม่จำเป็นต้องเปิดค้างเพื่อให้ระบบทำงาน

> ส่วนแผนพัฒนาด้านล่างเก็บไว้เป็นประวัติการออกแบบก่อนย้าย Model A ลง Firmware; ขั้นย้ายลง ESP32 เสร็จแล้วใน Firmware 0.12.2

## ข้อมูลที่ควรบันทึกในการทดลอง

แต่ละรอบควรเก็บ:

- เวลาและรหัสข้อมูลเซ็นเซอร์
- อุณหภูมิและ lux
- ตำแหน่ง Encoder ก่อนตัดสินใจ
- Preset/Model ที่ใช้
- Action และเป้าหมายที่เสนอ
- เหตุผลการตัดสินใจ
- Confirmation ปัจจุบัน
- Cooldown ที่เหลือ
- ตำแหน่งหยุดจริงและค่าคลาดเคลื่อน
- Limit/fault ที่เกิดขึ้น
- ผู้ทดลองเห็นด้วยหรือไม่กับผล

ช่วงแรกไม่จำเป็นต้องใช้ฐานข้อมูลถาวร สามารถส่งออก JSON/ข้อความเพื่อเปรียบเทียบได้ เมื่อจำเป็นต้องดูผลหลายวันหรือหลายผู้ใช้จึงค่อยเพิ่ม SQLite/PostgreSQL

## แผนทีละขั้น

### ขั้น 1 — เปรียบเทียบแบบ Preview

- ให้ Auto ปัจจุบันและ Model A รับข้อมูลชุดเดียวกัน
- แสดงผลข้างกันโดยไม่สั่งมอเตอร์
- เพิ่มปุ่มบันทึกว่า “ผลนี้เหมาะสม/ไม่เหมาะสม”
- เก็บกรณีที่สองโมเดลตัดสินใจต่างกัน

เกณฑ์ผ่าน: หน้าเว็บต้องอธิบายได้ว่าทำไมแต่ละโมเดลเลือกผลนั้น และเซ็นเซอร์หายต้องไม่มีเป้าหมาย

### ขั้น 2 — Replay จาก Motion Log

- นำข้อมูลที่เคยบันทึกมาเล่นซ้ำ
- ตรวจว่า Model A ให้ผลเดิมเมื่อรับลำดับข้อมูลเดิม
- ตรวจจุดขอบ 200 lux และขอบอุณหภูมิ 26/28/30/31°C

เกณฑ์ผ่าน: ผลต้อง deterministic และไม่มีเป้าหมายนอก 0–100%

### ขั้น 3 — Continuous Test บนหน้า Dev

- ผู้พัฒนายืนยันความปลอดภัยหนึ่งครั้งก่อนเริ่ม Runtime
- ระบบยืนยันผล 2 รอบ ส่งเป้าหมายหนึ่งคำสั่ง และรอ Encoder หยุดจริง
- พัก 15 วินาทีแล้วจึงประเมินข้อมูลรอบถัดไป
- การซ่อนแท็บ เปลี่ยน Manual หรือพบ blocker ต้องหยุด Runtime

เกณฑ์ผ่าน: ทำงานวนได้โดยไม่มีคำสั่งซ้อน STOP ใช้ได้ และ FC-33 หยุดได้ทุกครั้ง

### ขั้น 4 — ปรับ Runtime Guard จากผลทดสอบ

- ปรับจำนวน Confirmation และ Cooldown จาก Motion Log
- เพิ่ม command timeout
- เพิ่ม maximum moves per hour เพื่อป้องกันการขยับถี่ผิดปกติ

เกณฑ์ผ่าน: ค่าเซ็นเซอร์แกว่งไม่ทำให้ม่านสั่นกลับไปมา

### ขั้น 5 — ย้าย Model A เข้า ESP32 หลัง Feature Flag

- สร้างตัวเลือก `decisionModel = preset | model-a`
- เก็บ State ของ Model A ใน ESP32
- เมื่อ reboot ต้องเข้าสถานะปลอดภัยและตรวจ calibration ก่อน
- ถ้า Model A fault ให้ปิด Auto หรือ fallback ตามนโยบายที่กำหนดไว้

เกณฑ์ผ่าน: ทำงานได้โดยปิดเว็บ และกลับ Auto Preset เดิมได้โดยไม่แฟลช firmware ใหม่

### ขั้น 6 — Controlled Always-on Test

- ทดสอบในช่วงเวลาจำกัดและมีผู้ดูแล
- เริ่มด้วยความเร็วมอเตอร์ต่ำ
- จำกัดช่วงตำแหน่งก่อน เช่น 20–80%
- ตรวจ Log หลังทุกชุดทดสอบ

เกณฑ์ผ่าน: ผ่านสถานการณ์ปกติ เซ็นเซอร์หาย Wi-Fi หลุด Encoder ผิดปกติ ลิมิตทำงาน และ STOP

## Safety checklist ก่อนทดสอบมอเตอร์ทุกครั้ง

- [ ] Encoder calibrated และตำแหน่งสมเหตุสมผล
- [ ] FC-33 ด้านเปิดและปิดแสดงสถานะถูกต้อง
- [ ] กด STOP แล้วมอเตอร์หยุดทันที
- [ ] ไม่มี motor fault ค้างอยู่
- [ ] มอเตอร์หยุดอยู่ก่อนส่งคำสั่งใหม่
- [ ] ความเร็วทดสอบอยู่ระดับต่ำ
- [ ] ไม่มีสิ่งกีดขวางหรือมืออยู่ในชุดส่งกำลัง
- [ ] เปิด Motion Log ไว้
- [ ] พร้อมตัดไฟ Adapter หากระบบผิดปกติ

## คำถามที่ต้องตัดสินใจก่อนใช้งานจริง

1. เมื่อ Model A ถึง `resolutionLimited` จะรอให้สภาพเปลี่ยนเท่าใดจึงปลดล็อกเอง
2. Model A ควรใช้ Confirmation กี่ครั้งและ Cooldown กี่วินาที
3. หากเซ็นเซอร์แสงหาย Auto ต้องคงตำแหน่ง ปิด Auto หรือ fallback เป็นอุณหภูมิอย่างเดียว
4. เมื่อ reboot ควร Home หาลิมิตทันทีหรือรอผู้ใช้ยืนยัน
5. ผู้ใช้สามารถปรับ Profile ของ Model A ได้ระดับใดโดยไม่ทำให้ระบบซับซ้อน

## งานที่แนะนำสำหรับรอบถัดไป

ใช้ Motion Log และ `/status.auto` บันทึกผลการทำงานกับม่านจริงเพิ่มเติม แล้วนำค่าคลาดเคลื่อน จำนวนครั้งที่กลับทิศ และเหตุการณ์ safety มาพิจารณาปรับ Confirmation, Cooldown และขนาด Step ในรุ่นถัดไป
